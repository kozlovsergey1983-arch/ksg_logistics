# КСГ — рабочее место экспедитора

Серверная версия для команды. Интерфейс на русском языке, Москва и перевозки по России, машины 10/20 т: тент, изотерм, рефрижератор.

## Что готово

- Вход по логину и паролю, главный администратор, администраторы и сотрудники.
- Добавление сотрудников, временные пароли, обязательная смена при первом входе.
- Отключение доступа, смена роли, сброс пароля и завершение сеансов.
- Общая база грузов, машин, контрагентов, сделок, звонков, шаблонов и заметок.
- Поиск, фильтры, сравнение вариантов, статусы, разница ставок, экспорт/импорт JSON.
- Проверка контрольных цифр ИНН и ссылки на бесплатные реестры; чек-лист документов.
- Журнал входов и изменений. Конфликт версии предотвращает перезапись чужих изменений.

Автоматического поиска заявок в ATI, проверки подлинности документов и отправки писем нет. Звонки отображаются в приложении; push-, SMS- и почтовые уведомления не подключены. Все сотрудники имеют доступ к общей рабочей базе. Персональных баз или доступа только к «своим» сделкам пока нет.

## 1. Загрузка кода в GitHub

1. Распакуй `KSG-CRM-server.zip` на компьютере.
2. Открой `kozlovsergey1983-arch/ksg_logistics`, вкладку **Code**.
3. Выбери **Add file → Upload files**.
4. Перенеси **содержимое архива**: `Dockerfile`, `server.py`, `requirements.txt`, `seed.json`, папку `public` и остальные файлы. В корне репозитория должен появиться `Dockerfile`, а не ZIP и не дополнительная папка `ksg-crm`.
5. Сохрани изменения кнопкой **Commit changes** в ветку `main`.

Не добавляй в GitHub пароли, строку подключения к базе или настоящий `.env`. В архиве нет рабочих паролей и клиентских данных. `.env.example` содержит только образцы названий настроек.

## 2. Размещение в Timeweb Cloud

Код: Python 3.12 + Flask, веб-сервер Gunicorn, постоянная база PostgreSQL. Для размещения выбирается **Dockerfile**, а не React/Next.js и не статический frontend. Возможности и стоимость приложения и PostgreSQL проверь до заказа ресурсов.

1. Создай отдельную базу **PostgreSQL** в Timeweb Cloud в выбранном российском регионе. Не используй существующую чужую базу с рабочими таблицами. Сохрани реквизиты подключения у себя.
2. В App Platform подключи репозиторий `ksg_logistics` и ветку `main` с загруженными файлами.
3. Выбери развёртывание через **Dockerfile**. Путь: `Dockerfile` в корне репозитория. Если текущая форма показывает только список frontend-фреймворков, вернись к выбору типа приложения и выбери Dockerfile.
4. Порт контейнера — **8080**, путь проверки состояния — **/healthz** (если панель предлагает такую настройку). Команды сборки/запуска уже заданы в Dockerfile.
5. В переменных окружения приложения задай:

| Имя | Что указать |
|---|---|
| `APP_ENV` | `production` |
| `PORT` | `8080` |
| `DATABASE_URL` | Строка подключения к созданной PostgreSQL, доступной приложению |
| `SECRET_KEY` | Собственная случайная строка, минимум 32 символа (лучше 64), одна для всех экземпляров приложения |
| `ADMIN_LOGIN` | `admin` либо свой логин латиницей |
| `ADMIN_NAME` | `Сергей` или имя главного администратора |
| `ADMIN_PASSWORD` | Собственный уникальный временный пароль, 12–256 символов |

Пример **формата**, не готовые реквизиты:

```text
postgresql://USER:PASSWORD@HOST:5432/DATABASE?sslmode=require
```

Используй строку подключения и сетевые настройки из панели своей базы. Спецсимволы в логине/пароле URL должны быть URL-кодированы. Для публичного подключения требуется TLS; при наличии CA у провайдера используй `sslmode=verify-full` и путь к CA. В частной сети доступ к БД настрой только из сети приложения. Не открывай PostgreSQL всему интернету для обхода сетевой ошибки.

6. Запусти сборку и дождись рабочего статуса. Открой **HTTPS**-адрес, выданный Timeweb. Таблицы создаются при первом старте автоматически; главный администратор создаётся только в пустой базе.
7. Войди с `ADMIN_LOGIN` и временным `ADMIN_PASSWORD`, затем сразу задай новый пароль в форме приложения. Введи новый пароль при повторном входе.
8. После первого успешного входа можно удалить `ADMIN_PASSWORD` из переменных приложения: он нужен только для первичного создания владельца. Смена этой переменной впоследствии **не сбрасывает** пароль существующего пользователя.
9. В разделе **Пользователи → Добавить пользователя** создай сотрудника и передай временный пароль лично. При первом входе сотрудник меняет его.

Если БД недоступна или настройки не заданы, приложение не запускается. SQLite разрешена только для разработки и тестов — на App Platform она не используется.

## 3. Контроль перед началом работы

- Войти администратором, создать сотрудника; сотрудник меняет временный пароль.
- Открыть сайт сотрудником в другом браузере/на телефоне. Создать заявку и увидеть её под администратором (кнопка «Обновить» либо автообновление, когда форма закрыта).
- Отключить сотрудника и проверить, что его следующий запрос/вход отклонён.
- Перезапустить приложение в Timeweb и убедиться, что заявка осталась.
- Включить резервные копии PostgreSQL у хостинга и проверить восстановление на отдельной тестовой базе.

## 4. Домен

Сначала проверь работу на техническом HTTPS-адресе. Затем в панели Timeweb добавь **crm.ksg-logistics.ru**. В NIC.RU внеси только записи для этого поддомена, которые выдаст **Timeweb**. Записи, ранее выданные для ChatGPT Sites, для этой версии не подходят. Не меняй записи основного домена, почты или NS без отдельного плана переноса зоны. Если `crm` уже указывает на старый хостинг, замени его запись при фактическом переключении.

## Резервные копии и восстановление

«Экспорт данных» выгружает **рабочие записи**, без паролей, пользователей и журнала. «Импорт» заменяет рабочие записи; сначала экспортируй текущие данные. JSON из старого HTML можно импортировать этой кнопкой. Старые локальные данные автоматически не переносятся.

Для полного восстановления нужны резервные копии **PostgreSQL**, которые включают пользователей и журнал, и сохранённая конфигурация приложения. Храни их отдельно от репозитория.

Если главный администратор потерял пароль, оператор хостинга может выполнить в окружении приложения:

```sh
python manage.py reset-owner
```

Команда спросит новый временный пароль без отображения в консоли и отзовёт старые сеансы. Передавать пароль аргументом команды не нужно. `DATABASE_URL` и `SECRET_KEY` должны быть настроены. Сотруднику пароль сбрасывается через раздел «Пользователи».

## Локальная разработка

Python 3.12 или новее. SQLite используется исключительно для локальных тестов. Рабочую конфигурацию хостинга не переводи в development.

```sh
python -m venv .venv
# Linux/macOS:
. .venv/bin/activate
pip install -r requirements.txt
export APP_ENV=development
export SECRET_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(48))')"
# Задай ADMIN_PASSWORD через переменную окружения, минимум 12 символов.
python server.py
```

Локальный адрес: `http://127.0.0.1:8080`. Для тестов без ручного ввода секретов:

```sh
python -m unittest -v test_server
```

Тестовые пароли находятся только в изолированных автотестах и не создают пользователей в рабочей БД.

## Документы

Пункт «Документы» находится в левом меню после «Заметки». Главный администратор
и администраторы публикуют файлы сразу. Сотрудники отправляют файлы на подтверждение:
до одобрения файл виден только автору и администраторам. Администратор может
подтвердить или отклонить файл с причиной. Отклонённый файл остаётся виден автору
и администраторам. Общий порядок опубликованных файлов меняется кнопками ↑/↓
только администратором. Удаление файлов доступно только администраторам.

Один файл — от 1 байта до 4 МБ. Любой формат скачивается вложением, без выполнения
в браузере. Запросы защищены сессией и CSRF; права проверяются на сервере.
Конкурирующие изменения отклоняются по версии списка. Все изменения записываются
в журнал. Файлы и метаданные хранятся в PostgreSQL (в тестовом режиме — SQLite),
новые таблицы создаются при запуске, новые зависимости не нужны.
Кнопка экспорта JSON рабочей базы не включает документы: для их резервного
копирования нужна резервная копия базы данных.

Новые файлы: documents.py, public/documents.js. Также обновлены server.py,
public/app.js, public/auth.js, public/index.html и public/style.css.

## Доработки CRM от 24 ноября 2026

- **Контрагенты.** Типы «Грузоотправитель», «Перевозчик» и «Оба» работают в одной карточке. Старый тип «Клиент» отображается как «Грузоотправитель» и записывается в новом виде при сохранении. Сопоставление использует ИНН без пробелов либо нормализованное название, когда хотя бы в одной карточке отсутствует ИНН. Существующие дубли остаются доступны для сверки вручную. Архив хранит карточку, основные и дополнительные телефоны и историю. При архивации освобождается назначение карточки, а незавершённые звонки исключаются из очереди. Причина и восстановление фиксируются в истории.
- **Мессенджер и календарь.** Общий чат и личные переписки открываются через один серверный аккаунт. Вложение загружается через авторизованный запрос, а права на скачивание совпадают с правами на переписку. Статус «онлайн» означает активность в последние 60 секунд. День, неделя и месяц используют время Москвы. Следующая задача создаётся при завершении повторяющейся задачи. Напоминания и уведомления приходят, пока веб-CRM открыта. Системные уведомления требуют разрешения браузера.
- **Android.** Сервер сохраняет прежний формат `GET /api/state` и смену статуса через `PUT /api/state` для режима `mobile:`. Мобильный веб-интерфейс использует ту же БД. Для отдельных экранов календаря и мессенджера внутри APK потребуются исходники Android-проекта и сборка, подписанная совместимым ключом.
- **Договоры.** Администратор загружает шаблон Word в реестр. Доступны поля `{{number}}`, `{{date}}`, `{{route}}`, `{{rate}}`, `{{cargo}}`, `{{payment}}`. Для каждой стороны есть `{{company.name}}` / `{{partner.name}}` и аналогичные ключи `inn`, `kpp`, `ogrn`, `address`, `bank`, `bik`, `account`, `correspondentAccount`. Свои реквизиты задаются через `CONTRACT_COMPANY_JSON`, реквизиты контрагента — в карточке. DOCX сохраняется при выпуске, PDF формируется из него при первом скачивании и сохраняется для повторной выдачи. Шаблоны проходят проверку перед загрузкой. Dockerfile устанавливает LibreOffice Writer и шрифты с кириллицей.
- **Диадок.** Пока отсутствуют токен и ящик в окружении, интеграция выключена. Для тестового ящика настройте `DIADOC_BOX_ID`, `DIADOC_ACCESS_TOKEN`, `DIADOC_SIGNER_LOGIN`. Токен OpenID Connect ограничен сроком действия. Отправка разрешена только администратору с указанным логином. Уполномоченный подписант скачивает PDF из реестра, подписывает именно этот файл во внешнем ПО и загружает отделённую подпись через форму Диадока. Ключ подписи хранится у подписанта. Права ящика, тариф, подпись и при необходимости МЧД проверяются с владельцем ящика в тестовом контуре. [Документация API и OpenID Connect](https://developer.kontur.ru/doc/diadoc-api/authentication) · [Интеграция по API](https://www.diadoc.ru/integrations/api) · [Условия тарификации](https://support.kontur.ru/diadoc/48976-tarify)

### Миграция и откат

Перед обновлением в Timeweb зафиксируйте текущий рабочий коммит и дождитесь статуса готовности свежей резервной копии всего кластера PostgreSQL. Экспорт JSON из интерфейса содержит рабочие коллекции. Для резервирования учётных записей, переписки, файлов и договоров нужна резервная копия PostgreSQL. При первом старте новая версия создаёт дополнительные таблицы и индекс. Старые таблицы и поля сохраняются.

Если сбой в приложении требует отката, разверните прежний рабочий коммит из истории деплоев Timeweb. Новые таблицы сохранят данные до следующего развёртывания. Восстановление старого снимка БД может потерять записи, сделанные после создания копии, поэтому сначала сохраните текущее состояние и проверьте восстановление в отдельной БД. [Резервные копии БД Timeweb](https://timeweb.cloud/docs/dbaas/dbaas-manage/backup) · [Управление деплоем](https://timeweb.cloud/docs/apps/deployment)
